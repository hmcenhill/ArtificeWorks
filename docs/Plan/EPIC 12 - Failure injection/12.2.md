## Kill a worker, poison a message: injecting into the pipeline itself

**Labels:** worker, backend, reliability, demo

## Summary

Light up the two broker-facing faults on 12.1's registry. **Kill a worker mid-task:** a handler
throws a one-shot transient before it acks, the message climbs the retry ladder, and the next
delivery — with the fault now disarmed — completes the order. **Poison a message:** a handler throws
`PoisonMessageException`, the message parks immediately into `dead_letters`, and it waits there for a
human to replay it. Both are pure wiring over Epic 8's machinery; the only genuinely subtle part is
making a fault fire *exactly once* across a rolled-back transaction.

## Why

This is the epic's headline: not "the system claims to recover" but "you broke it and watched it
recover." The transient fault is the faithful stand-in for a worker dying mid-pick — from the
broker's side, a handler that throws before acking is indistinguishable from a consumer that fell
over holding the message, and the redelivery-and-complete that follows is the real retry ladder
(8.2), not an animation. The poison fault is the other half of the reliability story: some failures
*can't* be retried away, and the honest answer is to park them somewhere a human can see and
reprocess — which 8.3 already built and 12.3 will make clickable.

Both reuse 12.1's registry unchanged. If either needs new recovery machinery, that is a finding about
Epic 8, not a licence to add a parallel path.

## Tasks

- [ ] **The consult point in the worker.** At the natural choke point for each stage — the top of the
      service method the handler calls, before the stage's work commits — consult the registry for a
      matching armed fault against this order. Keep it *one* place per stage, not scattered through
      the handler; the `Explore` sweep in the epic plan maps where that choke point is for picking and
      production. Which stage(s) each fault kind can target is a story-start decision — pick materials
      is the epic's literal "mid-pick"; production is an equally good demo. One stage done well beats
      three done shallowly.
- [ ] **`TransientOnce` → throw, climb, recover.** A matched fault throws an ordinary exception (the
      kind `RabbitMqConsumerService` already classifies as *transient* — a DB blip, a concurrency
      conflict), so the message goes to the 5s rung, is redelivered, and — the fault now disarmed —
      completes. No change to the consumer's failure taxonomy; the throw lands in the existing
      transient branch.
- [ ] **Disarm outside the rolled-back transaction — the one hard part.** The throw rolls back the
      stage's work, so if disarming rode that transaction it would roll back too and the fault would
      re-fire on every redelivery until the message *parks* — the opposite of "recover". So consuming
      the fault is a **separate, committed** write that happens before (or independently of) the
      throw. Prove it: an armed `TransientOnce` order fails attempt 1, then **completes on attempt 2**
      rather than climbing all three rungs and parking.
- [ ] **`Poison` → immediate park.** A matched fault throws `PoisonMessageException`, which the
      consumer already routes straight to `artifice.parked` with no retries (replaying a parse failure
      is the same failure again). The `ParkedQueueDrain` turns it into a `dead_letters` row carrying
      the order id — so it appears in `GET /system/dead-letters?workOrderId=…` with the injected reason
      as `LastError`. Nothing new in the drain; it is already the most defensive code in the system.
- [ ] **Consume-on-park semantics.** A poison fault parks and the message won't be redelivered, so the
      order sits in the DLQ until replayed — decide whether the registry entry is consumed at park
      time or cleared by the eventual replay/reset. Simplest honest choice: consume when it fires
      (12.1's one-shot rule), and the parked message is the durable evidence from there on.
- [ ] **Replay closes the loop.** The existing `POST /system/dead-letters/{id}/replay` republishes via
      the outbox at attempt 1; with the fault already consumed, the replayed message runs clean and
      the order completes — the dedupe keys (5.4/6.4/7.1) making a replay onto an already-done stage a
      safe skip, exactly as for any redelivery. No new endpoint; this is 8.3 doing its job.
- [ ] **Tests (integration, on the Testcontainers worker rig):** an armed `TransientOnce` order
      recovers on redelivery and reaches Delivery/Completed without parking; an armed `Poison` order
      lands as a `dead_letters` row with its order id and injected reason, and a subsequent replay
      drives it to completion; a fault fires once (a redelivery or a replay does not re-trigger it);
      neighbouring orders on the same queue are untouched while one is armed.
- [ ] Update [docs/messaging-topology.md](../../messaging-topology.md): the injection consult points
      as a labelled tap on the pipeline, and the note that injected transient/poison ride the
      *existing* ladder and parked-queue paths with no new topology.

## Acceptance Criteria

- [ ] An armed transient fault fails a stage once, the message is redelivered, and the order recovers
      to completion — it does **not** exhaust the ladder and park
- [ ] An armed poison fault parks immediately and appears as a `dead_letters` row against the target
      order, with a readable injected reason
- [ ] Replaying that dead letter drives the order to completion
- [ ] A fault fires exactly once — no redelivery, replay, or reset re-triggers it
- [ ] Injecting a fault into one order never disturbs another order on the same queue
- [ ] No new retry/park/replay machinery was added; the faults ride Epic 8's existing paths

## Decisions (to confirm at story start)

- **The disarm is committed independently of the stage's rolled-back work.** The single subtle
  correctness point in the epic. A fault consumed inside the transaction the throw rolls back re-fires
  forever and parks; the demo needs *recover*, so the consume is its own committed write. Assert the
  attempt-2 completion, not just the attempt-1 failure.
- **"Kill a worker" is a simulated death, said so plainly.** A real SIGKILL of a shared worker breaks
  the demo for everyone else; a throw-before-ack is the faithful, courteous stand-in and the copy
  (12.3) calls it what it is. Honesty principle over literalism.
- **Transient rides the ladder, not a nack-requeue.** The 5s rung is the built path and gives a
  visible dwell in a delay queue (which 11.4's diagram can show); an immediate nack-requeue would be
  faster but flashes past. Either is defensible — default to the ladder for legibility.
- **Pick one stage to inject well.** Materials-picking is the epic's literal "mid-pick"; production is
  an equally strong demo. Do one thoroughly; a stage selector for the rest is a later refinement.

## Notes

Depends on 12.1's registry (the enum values `TransientOnce` / `Poison` were reserved there). Reads
best with the worker running under the simulation so the redelivery-and-recover happens against a
moving factory. No frontend here — 12.3 puts the buttons on it and makes the dead letters clickable.
If injecting cleanly needs a registry field 12.1 didn't add (a stage selector), fold the migration in
here rather than guessing at it earlier.
