## Materials per attempt: a rebuild consumes real components

**Labels:** backend, domain, reliability

## Summary

Pay off the simplification Epic 6 took on and Epic 13 was named as the home for: widen the material
reservation key from `WorkOrderId` to `(WorkOrderId, AttemptNumber)`, and route the rework loop back
through picking so a rebuild draws the parts it burns. Nothing new is modelled — this is the same
pick, run once per attempt instead of once per order.

## Why

Physically, a scrapped automaton takes its components with it. Today it does not: `Build` on attempt 2
creates units out of nothing, because `material_reservations.WorkOrderId` is unique and a second pick
for an order is impossible. That was the right call in Epic 6 (the alternative was reopening Epic 5's
key mid-epic) and it is written down honestly in architecture.md's *Known simplifications* — but it is
the one place in the system where the model tells a small lie, and this epic is the deep-domain epic.

It also has to be first. 13.3 spawns a child work order **from a failed pick**, and a pick that can
only ever happen once per order gives that spawn nowhere to retry from. Making picking attempt-aware
is the foundation, not a side quest — and it is worth landing on its own, because the unique index it
changes is the one Epic 5 built its entire concurrency argument on.

## Tasks

- [ ] **`MaterialReservation` gains `AttemptNumber`.** Constructor takes it; `Describe()` mentions it
      where a timeline entry would otherwise read identically for two picks. Migration
      `AttemptScopedReservations`: add the column, drop the unique index on `WorkOrderId`, add a unique
      index on `(WorkOrderId, AttemptNumber)`. Existing rows backfill to attempt 1 — the only reading
      that is true of them.
- [ ] **`IMaterialReservationRepository` becomes attempt-aware.** `GetForWorkOrder` →
      `GetForAttempt(workOrderId, attemptNumber)`, and `TryReserve` takes the attempt. Keep a
      by-order query if a read path needs "everything ever drawn for this order" (the timeline
      probably does) — but the *write* path must not be able to ask a question that no longer has one
      answer. The interface's doc comment carries Epic 5's guarantees; restate (c) in attempt terms.
- [ ] **`MaterialPickingService.PickMaterials` takes an attempt number and a demand quantity.**
      Attempt 1 demands the full `OrderItemQty`; attempt N demands the **outstanding** quantity, which
      `ReworkRequired.OutstandingQty` already carries — take it from the event rather than re-reading
      the order, for the same reason the attempt number is derived and not read (6.4: a redelivery
      must compute the same demand). Duplicate detection, the all-or-nothing draw, the OnHold-on-short
      path and the metrics all keep their current shape.
- [ ] **Re-route the rework loop through picking.** `ReworkRequiredHandler` currently calls
      `ProductionService.Produce` directly. It now calls `MaterialPickingService.PickMaterials` for
      attempt `N + 1`; the pick publishes `MaterialsReserved`, and production is reached the same way
      it is on the first pass. This is what makes the loop a *real* cycle — the rebuild goes through
      every stage the original build did, not a shortcut past the expensive one.
- [ ] **`MaterialsReserved` carries `AttemptNumber`.** `MaterialsReservedHandler` stops hard-coding
      `InitialAttempt = 1` and reads it from the payload; delete the comment explaining why 1 was
      safe, because it no longer is. The event contract test should catch the shape change — check it
      does, and if it doesn't, that is a finding worth a line in 13.5's notes (Epic 14 owns the
      general answer).
- [ ] **Short on a rebuild.** An order that cannot get parts for attempt N goes OnHold with the
      reason, exactly as attempt 1 does — no new path, but *do* check the reason string reads
      correctly for a rebuild ("insufficient stock" on an order that is already InProcess is
      confusing without the attempt in it). The order sits at InProcess/OnHold with units short; a
      release re-triggers nothing today (7.3's narrow rule), which is a known and acceptable dead end
      until 13.3 gives shortages somewhere to go.
- [ ] **Check the chaos consult point still fires once.** `FireBrokerFaultIfArmed` sits at the top of
      `PickMaterials`, which now runs more than once per order. `TryConsume` is a one-shot conditional
      update, so an armed fault still fires on exactly one attempt — confirm with a test rather than
      by reading, because "the pick happens once" was an unstated premise of 12.2's design.
- [ ] **Tests.** Unit: demand for a rebuild is the outstanding quantity, not the order quantity.
      Integration (`MaterialPickingTests` / `ProductionInspectionTests`): a rework cycle draws a
      *second* reservation and on-hand falls twice; two deliveries of the same `ReworkRequired`
      produce one reservation for that attempt (the new unique index, proven the way 5.4 proved the
      old one); a rebuild that cannot get parts holds the order and draws nothing; an armed
      `TransientOnce` fault fires on one attempt only.
- [ ] **Update [docs/architecture.md](../../architecture.md)**: move attempt-scoped reservations out
      of *Known simplifications* into the dedupe-key invariant (picking is no longer the order-scoped
      example — it joins the run tables), and note that the rework loop now re-enters at picking.
      Update the pipeline diagram's rework arrow accordingly.

## Acceptance Criteria

- [ ] A rebuild draws components from stock; on-hand falls once per attempt, not once per order
- [ ] Two deliveries of the same rework event reserve once — the new unique index is the guarantee,
      not the pre-check
- [ ] A rebuild that is short of stock holds the order and draws nothing (all-or-nothing, unchanged)
- [ ] The rework loop reaches production *through* picking, with no second entry point into
      `ProductionService`
- [ ] An injected `TransientOnce`/`Poison` fault still fires exactly once for an order, across
      multiple picks

## Decisions (to confirm at story start)

- **Widen the key; don't add a second table.** A `pick_attempts` marker table alongside an
  order-scoped reservation would preserve the old index at the cost of splitting "what was drawn" from
  "that it was drawn" — and 5.4's best property is that the dedupe marker and the reservation are the
  same row. Widening keeps that.
- **Demand comes from the event, not the aggregate.** `ReworkRequired.OutstandingQty` is the number,
  for the same reason 6.4 derives the attempt from the event: a redelivery must compute an identical
  request or the unique index is guarding two different things.
- **Rework re-enters at picking, not at production.** The alternative — pick from the *inspection*
  service before it publishes `ReworkRequired` — would put a material draw inside the inspection
  stage's transaction and give picking two callers. One stage, one job.
- **No re-pick on release.** An order held short of parts on a rebuild stays held until someone
  releases it, and the release re-triggers nothing (7.3). Resist widening `RerequestShippingIfStranded`
  into a general "resume whatever you were doing" — that is a real design question, it belongs to
  whoever needs it, and 13.3 will want it phrased as "a parent whose child finished", not as a
  release hook.

## Notes

**Expect the shelves to drain.** With 10.2's `FailureRate` up, rebuilds are common, and this story
makes every one of them expensive. 10.4's sweep restocks to `seed_on_hand` so the world still heals,
but the seeded quantities in `CatalogSeeder` were sized for free rebuilds. If the demo starves after
this story, the fix is the seed data, not the design — say so in the handoff rather than quietly
raising the numbers.

This story touches the timeline and the dashboard only incidentally (a second "materials picked" line
appears per rebuilt order, which is correct and welcome). If the timeline read model assumes one
reservation per order, that is a finding to fix here rather than defer — a broken timeline on the
demo's most-clicked view is not a deferrable cosmetic.
