## Child work orders: making what we don't have

**Labels:** backend, domain, messaging

## Summary

The epic's headline. When a pick is short of a **made** component, the factory does what a factory
does: it schedules the sub-assembly. A child work order is created for the shortfall, the parent goes
OnHold waiting on it, the child runs the ordinary pipeline, and on passing inspection it is **stocked
rather than shipped** — crediting the component's on-hand, which releases the parent to re-pick and
carry on.

## Why

This is the acceptance criterion the epic exists for, and it is the moment the model stops being a
single-level order tracker and becomes a manufacturing system. It is also, on the dashboard, the best
thing this epic produces: a visitor creates one order and watches the board *deepen* — a second order
appears, runs, disappears into stock, and the first one resumes. Nothing else in the project shows
work begetting work.

The design earns its keep by how little it invents. A child is an ordinary `WorkOrder`. It runs the
ordinary stages. Its output is ordinary component stock, drawn by the ordinary atomic decrement. The
parent's wait is the ordinary OnHold. The only genuinely new things are: a parent link, one branch at
inspection-passed, and one subscriber that releases a parent when its child completes.

## Tasks

- [x] **`WorkOrder` gains a parent link.** `ParentWorkOrderId` (nullable), `ForComponentId` (what this
      child is making — null for a top-level order) and `ParentAttemptNumber` (which of the parent's
      pick attempts asked for it). A dedicated constructor or factory (`WorkOrder.ForSubAssembly(...)`)
      so a child cannot be created without all three, and so the domain — not a caller — decides that
      a child inherits its parent's `Origin`. Migration `SubAssemblyWorkOrders`.
- [x] **The dedupe key: one request per (parent, attempt, component).** A filtered unique index on
      `(ParentWorkOrderId, ParentAttemptNumber, ForComponentId)` where the parent link is not null.
      This is the rule architecture.md already states, applied to the new thing that must happen once:
      a redelivered scheduling event must not spawn a second child. As everywhere else, the index is
      the guarantee and any pre-check is only an optimisation.
- [x] **Spawn on a short *made* component.** In `MaterialPickingService`, the short path currently
      goes straight to OnHold. It now asks: are any of the short components made? For each one,
      create a child work order for the shortfall quantity (the demand minus on-hand, not the whole
      demand), advance it to Scheduled so it starts moving, and record the link. Then hold the parent
      with a reason that names what it is waiting for. **Bought** components short → OnHold exactly as
      today, unchanged. Decide at story start whether the child is created inside the pick's
      transaction or announced as an event; the `Explore` sweep in the epic's plan is for exactly this.
- [x] **Cap the depth.** A child may itself be short of a made component and spawn a grandchild —
      correct, and the seeded two-level catalog will do it. Cap the chain (reuse 13.2's `MaxDepth`
      constant) and route an over-deep order to `Fault` with an honest reason rather than spawning.
      Combined with 13.2's cycle refusal, this is the runaway guard; test it against a deliberately
      deep fixture.
- [x] **Putaway: an internal order is stocked, not shipped.** At `work-order.inspection-passed`, an
      order **with a parent** takes a different branch: a new `StockPutawayService` credits
      `components.on_hand` for `ForComponentId` by the passed quantity (an atomic conditional UPDATE,
      the same idiom as 10.4's restock and 5.3's draw), advances the child Delivery → Completed, and
      publishes `WorkOrderCompleted` so the announcement is the one the whole system already
      understands. No shipment row, no carrier, no tracking number. Idempotent per order — the child's
      terminal transition is the natural guard, but check it holds against a redelivery and add a key
      if it doesn't.
- [x] **Release the parent when the child completes.** A subscriber on `work-order.completed` for an
      order that has a parent: release the parent's hold and re-publish `work-order.scheduled` so it
      re-picks at its current attempt. 13.1 made picking attempt-aware, and the pick that failed drew
      nothing (all-or-nothing), so the retry is clean and the reservation index is untroubled. If the
      parent is waiting on more than one child, only the last one to finish should resume it — decide
      whether that is "release when no live children remain" (a query) or "try to re-pick and hold
      again if still short" (a retry). Prefer the second if it is honest: a re-pick that fails just
      holds again, and the system self-corrects.
- [x] **Parent cannot complete before its children.** Mostly falls out — the parent is held at picking
      — but make it explicit in the domain so the acceptance criterion is *proved*, not implied: the
      transition into `Completed` (and ideally out of Inspection) refuses while the order has live
      children. Belt and braces, in the house style: the guard the system does not rely on is the one
      that catches the bug the system did not foresee.
- [x] **The world sweep must not orphan a live child.** 10.4 retires old terminal/held/faulted orders.
      A parent held for hours waiting on a child is exactly the shape it retires — and retiring it
      would leave a child building parts for nobody, or cascade-delete a running order. Decide the
      rule (skip an order with live children; retire parent and children together only when the whole
      tree is terminal) and test it. This is the sharpest edge in the story.
- [x] **Make the relationship visible.** The order detail should show "made for order X" on a child
      and "waiting on N sub-assemblies" on a parent, with links both ways — this is 11.x's loop-closes-
      both-ways pattern and it is what makes the demo legible. The board should be able to tell a child
      from a top-level order at a glance (a badge; children inherit `Origin`, so the existing filter
      cannot do it). Small frontend surface, but it belongs here rather than in 13.4 — a spawned child
      nobody can see is a feature nobody can demo.
- [x] **Tests.** Integration is where this story lives: an order for a product whose made component is
      out of stock spawns exactly one child, holds the parent, and the child runs to Completed →
      on-hand rises → parent resumes → parent completes. Redelivery of the scheduling event spawns one
      child (the index). A grandchild chain works to the cap and Faults beyond it. The sweep leaves a
      parent with a live child alone. Unit: the domain refuses to complete a parent with live children;
      shortfall quantity is demand-minus-on-hand.
- [x] **Docs:** [docs/messaging-topology.md](../../messaging-topology.md) — the putaway branch and the
      new `work-order.completed` subscriber (it has had exactly one subscriber, the dashboard relay,
      since 11.2; that sentence changes). [docs/architecture.md](../../architecture.md) — parent/child
      as an invariant: a child is an ordinary order, its output is stock, its completion is the gate.

## Acceptance Criteria

- [x] A work order short of a made component spawns a child work order for the shortfall and goes
      OnHold naming what it waits for
- [x] The child runs the ordinary pipeline and, on passing inspection, is stocked rather than shipped
- [x] The parent resumes automatically when its children are done and completes normally
- [x] A parent cannot reach Completed while it has live children
- [x] A redelivered scheduling event spawns exactly one child
- [x] Sub-assembly depth is capped; an over-deep or cyclic BOM cannot generate work indefinitely
- [x] The world sweep never retires an order with a live child
- [x] Parent and child are visible to each other on the dashboard

## Decisions (to confirm at story start)

- **A child is an ordinary work order.** No `SubAssemblyOrder` type, no separate table, no parallel
  state machine. Everything the pipeline, the board, the timeline, the metrics and the chaos panel do
  for an order, they do for a child for free — which is the entire reason this story is one story.
- **The child inherits the parent's `Origin`.** The demand *is* the parent's: a visitor who orders a
  Courier has caused every unit of work beneath it, and splitting a third value out of a two-valued
  metric dimension (architecture.md's rule) to say "the factory asked itself" would make every
  origin-split panel wrong in a new way. Children are distinguished by their parent link, not by origin.
- **OnHold, not a new status.** The reason string carries "waiting on sub-assembly"; the state machine
  is untouched. Revisit only if the board genuinely cannot express the difference — and it can, via
  the parent link.
- **Stock, not allocation.** Confirmed at grooming: the child credits `on_hand` and the parent re-picks
  through the ordinary decrement. A made component is fungible; per-unit pedigree (which rim went into
  which wheel) is a real concept and a later story, not this one.
- **The parent's retry is a re-pick, not a resume.** Republishing `work-order.scheduled` reuses the
  trigger that already exists; there is no new "resume" verb and no partial state to reconstruct,
  because the failed pick drew nothing.

## What was actually built

Implemented 2026-07-31. The open questions the story left, and what they were answered with:

- **The child is created inside the pick's transaction, not announced as an event.** The short path
  already ends in a save that holds the parent, so joining it costs no second transaction, no new
  event type, and no intermediate state where a parent is held with nobody building for it.
  `WorkOrder.ForSubAssembly` attaches the child to the parent's `Children` collection, so the
  existing `IWorkOrderRepository.Update` commits the hold, the child, its state history and the
  `created`/`scheduled` outbox rows together. **No new repository method was needed** — the first
  version added a `TryAddChildren` that caught the unique violation and detached the losers, and the
  concurrency test showed that to be theatre: the winner's hold has already moved the parent's
  `xmin`, so the loser cannot cleanly commit anything anyway. It throws, 8.2 classifies it transient,
  and the redelivery finds the open request in the pre-check. Thirty-five lines deleted.
- **Resumption is "try to re-pick and hold again if still short"**, the story's preferred option, and
  it is honest because the dedupe index is **filtered to live children**. An absolute key would have
  refused a parent that legitimately needs to ask again (its child finished, another order took the
  stock) and left it waiting forever. The filter is a unique index on a mutable column — unusual
  enough that it is called out in messaging-topology.md rather than left to be discovered.
- **`WorkOrderScheduled` gained `AttemptNumber`**, and `Quantity` now means *outstanding*. A parent
  released after a failed rebuild pick is not asking for attempt 1 or for its whole ordered quantity,
  and 6.4's rule forbids the handler re-reading state to find out. For a freshly created order both
  readings are identical, so nothing else changed. The handler floors a zero attempt at 1 — a
  compatibility repair for a message staged before the field existed, not a re-derivation.
- **`WorkOrderCompleted`'s carrier and tracking number became nullable**, plus a `ForComponentId`. A
  stocked child has no parcel, and inventing a fictional carrier to avoid one nullable field would be
  a lie.
- **Depth is a stored `tree_depth` column**, not a recursive walk up the parent chain per pick. It
  shares 13.2's `MaxDepth` constant, so the read side's cap and the write side's cap are one number.
- **Seed levels were lowered for the two made components** (`CMP-CTRL-STACK` and `CMP-CORE-AETHER`
  300/320 → 24, `CMP-CASING-CORE` 320 → 12). This is the note at the bottom of this story acted on:
  with made components stocked like bought ones, a child order would never appear in a demo. 24 is
  roughly eight simulated orders. **These three numbers are the demo's pacing dial** and are
  commented as such in `CatalogSeeder`.

Two things the story asked for that were *not* separately built, because they fell out: `/system/stats`
needed no change (a child is an ordinary order and is counted as one), and the retire cascade's
foreign keys needed no new cascade — the sweep's predicate and a `NO ACTION` self-reference cover it.

## Notes

The riskiest interaction in this story is **not** the spawn — it is everything downstream that assumed
orders are independent: the world sweep (above), the board's limit, `/system/stats`' counts, and the
retire cascade's foreign keys. Budget time for the sweep specifically.

> The prediction was half right. The sweep itself was the easiest part to get correct, because
> writing the `NO ACTION` constraint *first* forced the predicate into the only shape that works:
> "every child is also being deleted by **this** statement", not the looser "every child is
> finished" — a terminal-but-not-yet-old child would survive the statement and the constraint would
> refuse the parent. The interaction that actually cost time was the one the story did not predict:
> the two **broker end-to-end test hosts** (`WorkerConsumerTests`, `InjectedFaultTests`) hand-mirror
> the worker's DI registrations, so adding a dependency to `InspectionPassedHandler` silently
> stalled five tests at inspection-passed. That duplication is a standing trap and a candidate for
> Epic 14.

Worth watching once it runs: with the simulation generating orders and made components starting
stocked, children only appear once the sub-assembly shelf drains. That is realistic but it makes the
showpiece hard to *demo on demand*. If it proves fiddly to trigger in front of someone, the honest
lever is a seed level low enough that it happens naturally — or a note for a future story that this is
what a "deplete a component" chaos lever would be for. Do not add that lever here.
