## The shared-platform payoff: the BOM explosion view

**Labels:** frontend, demo, api

## Summary

Make the company's central claim visible: a catalog view that explodes each product line into its
tree of sub-assemblies and raw components, and shows the **overlap** between Custodian, Delver and
Courier — the "70% shared platform" pitch, rendered from the actual data rather than asserted in
prose. Read-only, one small read endpoint plus a `web/` view.

## Why

Two stories of real domain depth have landed by now and none of it is visible: the tree is in the
database, the children flash past on the board. This story is where a stranger *sees* the model. It is
also the epic's natural check-in point — small, self-contained, no pipeline risk — and it is the last
thing that has to exist before routings, the epic's big optional half, gets started.

It follows 12.3's pattern exactly: the endpoints and the domain already exist, and the story's work is
making them clickable and honest.

## Tasks

- [ ] **The commonality read model.** One endpoint — `GET /catalog/commonality` (or
      `/products/commonality`; match the house routing style at story start) — returning, for the
      seeded product lines: each product's exploded leaf set, the components shared by *all* lines,
      the ones shared by some, and the ones unique to one. Computed from 13.2's explosion, not from a
      second hand-written walk. Include per-component on-hand so the view can show a shortage, and the
      made/bought flag so sub-assemblies read differently from raw parts.
- [ ] **A catalog view in `web/`.** New route (`/catalog`) and nav entry. Per product line: the
      exploded BOM as a tree — depth-indented, made components expandable to show what they are made
      of, each node carrying qty-per-unit and on-hand. This is the one place in the dashboard where
      the *design* of the automata is on screen rather than their traffic.
- [ ] **The overlap, shown as overlap.** A commonality panel: which components all three share, which
      two share, which are trade-specific — with the shared percentage stated and derived from the
      data on screen, not hard-coded. A small matrix or three-column grouping will read better than a
      Venn; pick at story start and keep it phone-legible, as 11.4 did.
- [ ] **Wire it to what already exists.** Reuse the existing client/typing conventions
      (`web/src/api/client.ts`, `types.ts`, the ProblemDetails→sentence mapper) and the existing card
      /section styling — no new design language. If a component is short, link it to the board filtered
      to the orders waiting on it, if that is cheap; otherwise leave the loop for later rather than
      inventing a query for it.
- [ ] **Make the pitch check itself.** The seeder's doc comment and `BillOfMaterialsTests` claim a
      shared percentage; this view now displays one. They must be the same number, from the same
      derivation. If they disagree, the test is right and the view is wrong — but the fact that they
      *can* disagree is worth one assertion pinning the endpoint's percentage to the domain's.
- [ ] **Tests.** API: the commonality endpoint returns the three lines with the expected shared set
      against the seeded catalog, and its percentage matches the domain's. Frontend: type-check and
      build (the bar 11.x/12.3 set — there is no lint script).

## Acceptance Criteria

- [ ] Each product line's full exploded BOM is viewable in the dashboard, sub-assemblies included
- [ ] The overlap across the three lines is shown, with a shared percentage derived from the data
- [ ] The percentage on screen, in the tests and in the seeder's stated claim are one number
- [ ] The view is read-only and adds no write surface
- [ ] `web` type-checks and builds

## Decisions (to confirm at story start)

- **One endpoint, not one per product.** The view's whole subject is the *comparison*; three round
  trips the client then intersects would put the domain rule in the browser, where the seeded catalog's
  claim cannot be tested.
- **Explosion lives in the domain, and this endpoint calls it.** No second walk in a query or a
  projection. 13.2 wrote the rule; a divergent copy in a read model is how the pitch and the data
  start to drift.
- **Read-only, and it stays that way.** Catalog *editing* (a visitor designing an automaton) is
  configure-to-order, which grooming explicitly kept in Epic 17. This story shows what is there.

## Notes

This is the smallest story in the epic and probably the highest portfolio-payoff per hour: it is the
one screen that says "this is a domain model, not a CRUD app". Give the copy the same care 12.3's
chaos panel got — name the sub-assemblies as things a factory would name, and let the shared platform
read as an engineering decision rather than a database fact.

Stopping the epic after this story leaves M6 closed and defensible: deepened domain, working
child-order loop, and the shared-platform story on screen. 13.5 is the extra mile.
