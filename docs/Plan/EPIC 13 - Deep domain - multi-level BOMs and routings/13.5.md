## Routings: production walks the operations, through work centers

**Labels:** backend, domain, messaging, demo

## Summary

Production stops being instantaneous. A product gets a **routing** — ordered operations (chassis fab →
core install → limb fitting → sensor calibration) each performed at a named **work center** — and the
production stage walks it step by step, announcing each operation as it completes. Work centers have
a capacity: a center that is full makes the next order wait its turn rather than running everything at
once.

**This is the epic's largest story and its timebox lever.** Everything before it demos on its own; if
time runs out, this is what gets cut.

## Why

"InProcess" is currently a single instant between two events. A real factory's production is a
sequence of operations contending for finite machines, and that sequence is what the words *work
center*, *capacity* and *queue* mean. Modelling it is the second half of the epic's DDD claim.

It also pays the demo directly. Epic 10's pace ladder applies per message hop, so an order that takes
four hops through production visibly *takes time to build* — and 11.4's architecture diagram gets four
pulses where it had one. The factory finally looks like it is doing work rather than teleporting.

## Tasks

- [ ] **`WorkCenter` and `Routing` (Domain).** `WorkCenter`: id, name, `Capacity` (how many operations
      may run at once), `InUse`. `Routing`: an ordered set of `Operation`s per product — sequence,
      name, work center, and a nominal duration if the pace model wants one. Seeded in
      `CatalogSeeder` alongside the catalog it already owns; give the three lines routings that share
      their platform steps and differ in the trade-specific ones, because that is the same story the
      BOM tells. Migration `RoutingsAndWorkCenters`.
- [ ] **`OperationRun`, keyed the way every other stage is.** Unique on
      `(WorkOrderId, AttemptNumber, Sequence)` — an operation runs once per attempt, and a rebuild
      (13.1) walks the routing again from the start. Same rule, third application; the row commits in
      the same `SaveChanges` as the work it guards.
- [ ] **The walk, contained inside the production stage.** `MaterialsReserved` starts operation 1
      instead of building units. Each completed operation publishes
      `work-order.operation-completed`, whose handler starts the next one. The **last** operation does
      what `ProductionService.Produce` does today — builds the units and publishes
      `work-order.production-completed`. Inspection, shipping, the rework loop and the dashboard's
      stage model therefore need no changes: the stage's entry and exit keys are the ones they already
      know. Keep the units-are-created-at-the-end reading unless there is a strong argument otherwise;
      creating serialized units mid-routing means partly-built units the domain has no vocabulary for.
- [ ] **`work-order.operation-completed`** — one new routing key, one line in `WorkOrderEventTypes`
      (the relay binds `All`, so the feed gets it for free), a hop in `web/src/domain/hops.ts` so the
      diagram pulses on it, and a feed label. Carries order id, attempt, sequence, operation name and
      work center — enough for the feed line to read like a factory floor report.
- [ ] **Capacity as an atomic claim.** Entering an operation claims a slot:
      `UPDATE work_centers SET in_use = in_use + 1 WHERE "Id" = @id AND in_use < capacity` — zero rows
      means full, authoritatively, exactly as 5.3's conditional decrement means "not enough". Leaving
      releases it. Add the matching check constraint (`in_use <= capacity`) in the house belt-and-braces
      style.
- [ ] **What a full work center does to the order — decide at story start, and write down why.** Two
      honest options, and they are genuinely different systems:
      1. **Wait and be pulled**: the order is recorded as queued at the center, and releasing a slot
         (on the previous operation's completion) starts the longest-waiting order. Event-driven, no
         polling, genuinely models a queue — and needs care that a release always pulls, or an order
         waits forever.
      2. **Wait and be re-offered**: the message goes back onto a delay rung and retries the claim.
         Trivial to build on 8.2's ladder, but it is *polling wearing a broker's clothes*, and a
         starved order can climb to the top rung and park in `dead_letters`, which would be a lie about
         what happened.
      Prefer (1) and budget for it; if it proves too large mid-story, (2) with the parking path
      explicitly disabled is an acceptable fallback that must be flagged in the handoff, not quietly
      shipped.
  - [ ] **Starvation and stalls are the failure mode to design against.** A slot leaked by a crashed
      handler permanently shrinks the factory. Decide the recovery: a sweep that releases slots held by
      operations with no live run, or deriving `InUse` from the runs themselves rather than storing it.
      Deriving is more robust and less "clever"; storing is faster to claim against. Whichever is
      chosen, there must be a way for the world to heal without a restart — 10.4's sweep is the natural
      home.
- [ ] **Show it.** The order detail's timeline should read as a routing (operation, work center,
      when), and a small work-center panel — each center, capacity, in use, queue depth — belongs
      either on the controls view or the architecture view. The capacity constraint is invisible
      without it, and an invisible constraint is not a demo.
- [ ] **Pacing check.** Each operation is now a hop, so a paced factory multiplies the per-order dwell
      by the number of operations. Confirm the resulting end-to-end time is watchable rather than
      tedious at the default pace, and say what you found — this may want a routing-aware default
      rather than a code change.
- [ ] **Tests.** Unit: the walk advances in sequence; the last operation builds and publishes
      production-completed; a rebuild re-walks from operation 1. Integration: an order traverses its
      full routing through real RabbitMQ and reaches inspection; a redelivered operation event runs the
      operation once (the unique key); with capacity 1 and two orders, the second waits and then runs —
      and *both* finish, which is the starvation test; a crashed operation does not leak a slot
      permanently.
- [ ] **Docs:** [docs/messaging-topology.md](../../messaging-topology.md) — the new routing key, the
      intra-stage loop and its queue. [docs/architecture.md](../../architecture.md) — routings as an
      invariant: the walk is contained between `materials-reserved` and `production-completed`, and
      capacity is a conditional claim in the same family as the reservation decrement.

## Acceptance Criteria

- [ ] Production progresses operation-by-operation through a product's routing, each step announced
- [ ] An operation runs exactly once per attempt, and a rebuild walks the routing again
- [ ] A work center at capacity makes further orders wait, and they all eventually run
- [ ] Inspection, shipping and the rework loop are unchanged — the stage's entry and exit keys are
      the same two as before
- [ ] The routing and the work centers' load are visible on the dashboard
- [ ] The pace ladder still produces a watchable end-to-end time

## Decisions (to confirm at story start)

- **The walk is inside the production stage.** Entered at `materials-reserved`, left at
  `production-completed`. This is the containment decision the whole story rests on: everything
  downstream keeps its contract, and a routing is depth rather than a new pipeline shape.
- **Units are built at the end of the routing.** Serialized units appear when the automaton exists.
  Modelling partly-built units would need a unit-level state machine that nothing in the demo reads.
- **Capacity is claimed with a conditional UPDATE.** The project's established answer to "check and
  act must be one operation". A row lock's worth of contention on a handful of work-center rows is
  fine at demo scale.
- **Capacity can be dropped, the routing walk cannot.** If the story is running long, a routing walked
  with unlimited capacity still satisfies "production progresses operation-by-operation" and still
  looks excellent. Cut capacity, keep the walk, and say so.

## Notes

Two things to be suspicious of while building this:

- **Message volume.** Four operations per attempt multiplies the pipeline's message count by roughly
  four, and the rework loop multiplies it again. The outbox, the dispatcher's ~1s poll and the retry
  ladder all handle it, but `/system/stats`, the feed's cap and the diagram's pulse cap were all sized
  for the old volume. Check them rather than assuming.
- **The temptation to make operations configurable.** A routing editor, per-order routing overrides,
  operation-level chaos levers — all plausible, none in scope. Seeded routings, walked correctly, is
  the whole of this story.
- **`EventContractTests` catches an event's shape change by compiling, not by asserting** (found at
  13.1, when `MaterialsReserved` gained `AttemptNumber`). The payloads are positional records, so a
  new field breaks every construction site — which is a real guard, but only for *required* fields.
  A field added with a default would round-trip completely untested, because each test asserts
  field-by-field rather than comparing the whole payload. Worth knowing before this story adds
  operation fields to `ProductionCompleted`; the general answer (schema versioning) is Epic 14's.

If this story is cut, leave this file in place with a line in the epic saying so. A groomed story that
was deliberately not built is a better artefact than a deleted one — it shows the timebox was a
decision.
